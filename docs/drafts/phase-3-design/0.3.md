## 0.3 Refine vs Extraction: Conceptual Clarification

The system contains two distinct LLM-driven operations. Understanding their differences is essential for design decisions.

| Dimension | Refine (精炼) | Extraction (提取) |
|-----------|---------------|-------------------|
| Input | Raw observations | Raw observations |
| Output | Improved observations (same type) | **New type** of structured data (`extracted_*`) |
| Operation | Merge duplicates, rewrite, delete low-quality, score | Extract structured facts from multiple observations |
| Granularity | Single or few observations | Batch (multiple observations → one result) |
| Goal | Clean noise, reduce redundancy | Understand semantics, create new knowledge |
| Changes format? | ❌ No | ✅ Yes (observation → structured JSON) |

**Core difference**:
```
Refine:     observation → observation (optimize)
Extraction: observations → structured facts (transform)
```

**Analogy**:
- Refine = editing an article (fix typos, merge paragraphs)
- Extraction = extracting key points from an article (summary, keywords, facts)

**Relationship**: Refine is a **prerequisite** for Extraction.
1. First refine observations (delete noise, merge duplicates)
2. Then extract structured data from refined observations

This ordering is present in `deepRefineProjectMemories()` (Section 9.2), which refines
first and then triggers extraction on the refined state. Condensed from
`MemoryRefineService:213-292`:

```java
// Step 1: Refine existing memories
if (!candidates.isEmpty()) {
    refineObservations(candidates, projectPath);
}
// Step 2: Run extraction on refined state — a separate, independently locked block
if (extractionService != null) {
    // ... lock.tryLock(0, ...) ...
    extractionService.runExtraction(projectPath);
}
```

**This ordering has never actually run.** `deepRefineProjectMemories()` has zero
callers in `backend/src/main` — the only four references outside its own definition
are comments (`MemoryRefineService:171,255` and `StructuredExtractionService:113,120`).
The two live extraction entry points both bypass refinement entirely:

| Entry point | Path | Refines first? |
|-------------|------|----------------|
| `POST /api/extraction/run` | `ExtractionController:172` → `runExtraction` | No |
| `PATCH /api/session/{sessionId}/user` | `SessionController:327` → `reExtractForSession` → `tryExecuteWithProjectLock` | No |

So the relationship above describes the design intent and the code that was written
for it, not the behaviour of a running system. Section 9.2 records the same status
("implemented but unreachable"); see also P2-12.

**Token cost profile** (Section 23):
- Refine dominates cost — N LLM calls, one per observation
- Extraction is cheaper in absolute terms — M LLM calls, batch of 20 observations per call

> The originally stated split (refine 97%+, extraction <3%) is arithmetically correct
> for its own inputs but rests on an incremental-extraction assumption that was never
> implemented. Extraction re-sends the newest 100 candidates on every run, so at
> steady state it costs ~5× the incremental figure. With the one template the shipped
> configuration actually enables, that leaves the split essentially where it started:
> **~97.5% / ~2.5%** (GPT-4o-mini). An earlier revision of this note said 89%/11%; that
> figure came from also assuming five enabled templates, and the configuration declares
> exactly one (`user_preference`). See Section 23.2 and 23.4.
