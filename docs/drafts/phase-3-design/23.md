## 23. Token Cost Analysis & Cost Control (v23)

This section provides a comprehensive token consumption analysis for both extraction and refinement pipelines, and proposes cost control strategies.

### 23.1 Token Consumption Model

**Per LLM call breakdown (extraction):**

| Component | Tokens | Notes |
|-----------|--------|-------|
| System prompt (template) | ~300 | Template prompt + instructions |
| Schema hint | ~200 | JSON Schema in user prompt |
| Per observation | ~100-200 | Title + content + metadata |
| Batch of 20 observations | ~2000-4000 | 20 × 100-200 |
| **Total input per batch call** | **~2500-4500** | System + schema + observations |
| **LLM output per batch** | **~300-800** | Structured JSON response |

**Per LLM call breakdown (refinement):**

| Component | Tokens | Notes |
|-----------|--------|-------|
| System prompt | ~200 | Refinement instructions |
| Observation content | ~100-500 | Single observation to refine |
| **Total input per call** | **~300-700** | |
| **LLM output per call** | **~100-300** | Refined content |

### 23.2 Extraction Cost Estimates

**Scenario: 5 templates × 3 projects, medium usage**

| Phase | Observations | Batches/Template | Total Calls | Frequency |
|-------|-------------|-----------------|-------------|-----------|
| Initial run (capped) | 100/project | 5 calls | 5 × 5 × 3 = 75 | Once |
| Daily incremental | ~10 new/project | 1 call | 5 × 3 × 1 = 15/day | Daily |

> **Correction (verified against source and a live database): the "Daily incremental"
> row does not describe the implemented system.** There is no incremental state of any
> kind — no watermark, no `NOT EXISTS` against prior results, no dedup. Every run
> re-selects the *newest* 100 matching observations and re-sends them to the LLM
> whether or not they were extracted before.
>
> - `ObservationRepository.findBySourceIn` is the only candidate query on the
>   `runExtraction` path: `WHERE project_path = :project AND source IN (:sources)
>   ORDER BY created_at_epoch DESC LIMIT :limit` (default 100). It references no
>   extraction state.
> - `findNewObservations(project, sources, sinceEpoch)` — the repository method that
>   *would* implement incrementality — has **no callers**.
> - Measured on a real database (18,373 extraction runs): of 3,885 distinct
>   observations ever used as extraction input, **3,880 (99.9%) were sent more than
>   once**; the worst case was **689 times**.
>
> The "once / daily" split above is therefore inverted: the initial-run cost is the
> **steady-state** cost. A project with ≥100 matching observations pays the full
> candidate window on *every* run, forever.
>
> The "5 calls" figure assumes a single user. Candidates are grouped by user
> (`groupByUser`, via session → `user_id`) and batched **per user**, so the real count is
> `Σ_users ceil(n_u / 20)` — 5 for a single-user project, more as users proliferate. The
> extreme, 100 candidates across 100 users, costs 100 calls rather than 5. The tables
> below use 75 calls/run, i.e. the single-user reading.

**Cost per day (incremental only, GPT-4o pricing):**

| Model | Cost/Call | Daily Cost | Monthly Cost |
|-------|-----------|------------|--------------|
| SiliconFlow (cheap) | ~$0.0001 | $0.0015 | $0.045 |
| GPT-4o-mini | ~$0.0005 | $0.0075 | $0.23 |
| GPT-4o | ~$0.01 | $0.15 | $4.50 |
| Claude 3.5 Sonnet | ~$0.008 | $0.12 | $3.60 |

> **What these numbers should actually be.** The table above prices 15 calls/day. The
> implemented system spends 75 calls on every run regardless of how much new material
> exists (5 templates × 3 projects × 5 batches of 20 for a single-user project; the cap
> on the candidate side is `EXTRACTION_MAX_CANDIDATES=100`). At one run per day, the
> steady-state figures are:
>
> | Model | Cost/Call | Calls/Day | Daily Cost | Monthly Cost | vs. above |
> |-------|-----------|-----------|------------|--------------|-----------|
> | SiliconFlow (cheap) | ~$0.0001 | 75 | $0.0075 | $0.23 | 5.0× |
> | GPT-4o-mini | ~$0.0005 | 75 | $0.0375 | $1.13 | 4.9× |
> | GPT-4o | ~$0.01 | 75 | $0.75 | $22.50 | 5.0× |
> | Claude 3.5 Sonnet | ~$0.008 | 75 | $0.60 | $18.00 | 5.0× |
>
> The per-call price is unchanged — the batch is still 20 observations — so the whole
> correction is in the call count. Note the cap cuts both ways: because candidates are
> capped at 100, cost stops growing once a project exceeds 100 matching observations.
> The savings come entirely from observations that are **never** extracted (§23.2b).

**Cost for initial run (one-time):**

| Model | 75 calls | Cost |
|-------|----------|------|
| SiliconFlow | 75 × $0.0001 | $0.0075 |
| GPT-4o-mini | 75 × $0.0005 | $0.0375 |
| GPT-4o | 75 × $0.01 | $0.75 |

### 23.2b The Cost Cap Is Also a Coverage Cliff

The 100-candidate cap that keeps cost bounded has a consequence that is easy to miss
when reading the tables above, because it shows up as a *saving* rather than a loss.

The candidate window is `ORDER BY created_at_epoch DESC LIMIT 100` — the **100 newest**
matching observations. Combined with the absence of dedup (see §23.2), every run
re-processes that same window, and the window only ever moves **forward** in time:

1. Run 1 selects observations #1–#100 (newest first).
2. Ten new observations arrive.
3. Run 2 selects #11–#110. Observations #1–#10 fall out of the window.
4. Because the window is defined by recency rather than by what remains unextracted,
   #1–#10 can never re-enter it. They are not "deferred to a later run" — they are
   **excluded forever**.

So once a project accumulates more than 100 matching observations, the oldest ones
stop being extracted permanently and silently. Nothing reports this: `runExtraction`
logs a candidate count and returns normally, and there is no queue of pending work
to drain later, precisely because the candidate query is the only definition of
"work to do".

This reframes the cost figures. The 5× is not extraction being repeated — it is the
*same* material being repeated *instead of* older material being reached. An
implementation that tracked a watermark (`findNewObservations` already exists for this)
would cost the same in the steady state and cover the whole history, because it would
process each observation once instead of re-sending the newest 100 forever.

**Coverage summary (runExtraction path only):**

| Matching observations in project | Batches per run | Observation's extraction fate |
|----------------------------------|-----------------|------------------------------|
| ≤ 20 | 1 | extracted on first run |
| 21 – 100 | 2 – 5 | extracted once the window reaches them |
| > 100 | 5 (capped) | newest 100 re-extracted every run; the rest never extracted |

### 23.3 Refinement Cost Estimates

**Scenario: 100 observations/session, 10 sessions/day**

| Operation | Calls/Observation | Calls/Session | Calls/Day |
|-----------|-------------------|---------------|-----------|
| Merge (2 obs merged into 1) | 0.5 | 50 | 500 |
| Rewrite | 1 | 10-20 | 100-200 |
| Quality scoring | 0 (no LLM) | 0 | 0 |
| **Total refinement** | | **60-70** | **600-700** |

**Daily refinement cost:**

| Model | Cost/Call | Daily Cost | Monthly Cost |
|-------|-----------|------------|--------------|
| SiliconFlow | ~$0.0001 | $0.06 | $1.80 |
| GPT-4o-mini | ~$0.0005 | $0.30 | $9.00 |
| GPT-4o | ~$0.01 | $6.00 | $180 |

### 23.4 Total Monthly Cost (Combined)

**Scenario: 5 templates × 3 projects × 10 sessions/day × 100 obs/session**

| Component | GPT-4o-mini | GPT-4o |
|-----------|-------------|--------|
| Extraction (incremental) | $0.23 | $4.50 |
| Refinement | $9.00 | $180 |
| **Total** | **$9.23** | **$184.50** |

**Key insight**: Refinement dominates the cost (97%+). Extraction is cheap by comparison.

> **Corrected totals.** Extraction is priced with the incremental assumption that §23.2
> shows does not hold. Using the steady-state figures instead:
>
> | Component | GPT-4o-mini | GPT-4o |
> |-----------|-------------|--------|
> | Extraction (steady state, 1 run/day) | $1.13 | $22.50 |
> | Refinement | $9.00 | $180 |
> | **Total** | **$10.13** | **$202.50** |
>
> Refinement still dominates, but by **~89%**, not 97%+. The gap is narrower than
> stated, and the two components scale differently: refinement cost tracks real new
> material, while extraction cost is pinned at the cap no matter how little new
> material exists. In a project with little activity, extraction can be the *larger*
> of the two — it keeps paying for the newest 100 observations even when the project
> has produced nothing new for a week.
>
> **A second live trigger is not priced at all.** `reExtractForSession`, reached via
> `PATCH /api/session/{id}/user`, does not use the batching loop. It calls
> `extractByTemplate` once per template with the **entire** session's source-filtered
> observations in a single prompt, subject to neither `EXTRACTION_BATCH_SIZE` nor
> `EXTRACTION_MAX_CANDIDATES`. A 60-observation session therefore costs one call with
> roughly 3× the input of a 20-observation batch — against a per-call price derived
> from 20. Both live triggers are event-driven (`POST /api/extraction/run` and the
> session PATCH); no scheduler invokes extraction.

### 23.4b Impact of Append-Only Extraction (Section 24.6)

If the append-only approach (Solution D) from Section 24.6 is adopted, extraction costs decrease further because no prior context is passed to the LLM:

| Approach | Prior tokens | New obs tokens | Total input | Cost/Call (GPT-4o-mini) |
|----------|-------------|----------------|-------------|------------------------|
| Current (truncated prior) | ~500 | ~2000 | ~2500 | ~$0.0005 |
| Current (full prior) | ~5000 | ~2000 | ~7000 | ~$0.0014 |
| **Append-only (proposed)** | **0** | **~2000** | **~2000** | **~$0.0004** |

**Net effect**: ~20% extraction cost reduction + elimination of data loss risk. The append-only approach is strictly better on both dimensions — cheaper AND safer.

**Note**: These extraction costs remain negligible compared to refinement costs regardless of approach. The primary motivation for append-only is safety (Section 24.6), not cost.

### 23.5 Cost Control Strategies

**Strategy 1: Frequency Control**

> **Frequency control by schedule was designed but never implemented.** The rows
> and the YAML below describe an intended design, not shipped behaviour. The
> backend has no cron schedule and no extraction timer; the real frequency
> levers are in Strategy 2 and Section 23.7.

| Mechanism (designed) | Default | Low-Cost | High-Frequency |
|-----------|---------|----------|----------------|
| Extraction schedule | Daily (2am) | Weekly | Every 6 hours |
| Refinement trigger | Every SessionEnd | Only on deep refine | Every SessionEnd |
| Deep refine schedule | Daily | Weekly | Daily |

```yaml
# NOT READ BY THE BACKEND — recorded as the original design intent.
# Neither app.memory.extraction.schedule nor app.memory.refine.deep-refine-schedule
# exists as a configuration key. Setting them is silently ignored.
app.memory.extraction:
  schedule: "0 0 2 * * ?"          # Daily at 2am (default) — never implemented
  # schedule: "0 0 2 * * 1"        # Weekly on Monday (low-cost)
  # schedule: "0 0 */6 * * ?"      # Every 6 hours (high-frequency)

app.memory.refine:
  deep-refine-schedule: "0 0 3 * * ?"  # Daily at 3am — never implemented
  # deep-refine-schedule: "0 0 3 * * 1"  # Weekly (low-cost)
```

What ships instead: refinement runs on a fixed rate
(`app.memory.refine-schedule-interval-ms`, default 300000 = every 5 minutes)
and calls `quickRefine(project, 10)`. Extraction runs only on the two
event-driven call sites listed in Section 23.7.

**Strategy 2: Batch Size Control**

```yaml
app.memory.extraction:
  initial-run-max-candidates: 100   # NOT "first run" — applies to EVERY run
  max-observations-per-batch: 20    # Batch size for LLM calls (per user)
  max-batches-per-template: 10      # Cannot bind at the defaults above
```

> **Two of these three comments are wrong.**
>
> - `initial-run-max-candidates` is named for a first run and the design assumed
>   incrementality would make later runs cheap. There is no incrementality
>   (§23.2), so this cap is re-applied on every invocation and *is* the steady-state
>   limiter. The name actively misleads: setting it to 0 disables extraction
>   entirely rather than only skipping an initial pass.
> - `max-batches-per-template: 10` **cannot take effect at the shipped defaults**. The
>   loop bound is `i < min(userObs.size(), batchSize * maxBatchesPerTemplate)`, and
>   `userObs` is a slice of the candidate list, which `initial-run-max-candidates`
>   already caps at 100. So a single user can never exceed 100 observations, hence at
>   most `ceil(100 / 20) = 5` batches — 10 is unreachable. It only begins to bind once
>   the candidate cap is raised above `EXTRACTION_BATCH_SIZE × EXTRACTION_MAX_BATCHES`
>   (200, with the shipped defaults), so raising either value in isolation does
>   nothing. The only control that binds out of the box is
>   `initial-run-max-candidates`.
>
> Both batch counters also apply **per user**, not per template, since grouping
> happens before the batching loop. See §23.2 for the call-count consequence.

**Strategy 3: Model Selection**

> **Per-subsystem model selection was designed but never implemented.** Neither
> `app.memory.extraction.model` nor `app.memory.refine.model` exists as a
> configuration key — neither in `application.yml` nor in any `@Value`. More
> fundamentally the capability is absent: `SpringAiConfig` declares a **single**
> `ChatModel` bean (`openAiChatModel`), and all six services that call the LLM
> (`AgentService`, `LlmQualityScorer`, `LlmService`, `MemoryRefineService`,
> `StructuredExtractionService`, `SummaryGenerationService`) go through it. One
> model serves observation generation, summarisation, scoring, refinement and
> extraction alike, so making extraction cheaper today means making *everything*
> cheaper. The YAML below is the original design intent.

```yaml
app.memory.extraction:
  model: "gpt-4o-mini"              # Cheaper for extraction — NOT READ
  # model: "gpt-4o"                 # Higher quality, higher cost

app.memory.refine:
  model: "gpt-4o"                   # Higher quality for refinement — NOT READ
```

**Strategy 4: Incremental Extraction (Designed, Not Implemented)**

> **Incremental extraction does not exist in the backend.** Section 7.1 proposes
> it; it was never built. There is no `extraction_state` row type anywhere in the
> code, and `StructuredExtractionService:211` selects candidates with
> `findBySourceIn(projectPath, sources, initialRunMaxCandidates)` — the newest N
> matching observations on **every** run, with no "since last extraction" filter.
> `ObservationRepository.findNewObservations(project, sources, sinceEpoch, limit)`
> does exist, is documented as "for incremental extraction", and has **zero
> callers** — the V16 migration even created the composite index to serve it.
> Note what the shipped query actually does: `ORDER BY created_at_epoch DESC`
> means new observations *do* get picked up, but the oldest ones beyond the cap
> are never extracted at all. The "primary cost reduction mechanism" below is
> therefore a plan, not a shipped property.

**Strategy 5: Cost Budget & Alerting (Designed, Not Implemented)**

> **There is no cost tracking or budget enforcement.** `app.memory.cost` does not
> exist as a configuration key, and neither `CostConfig` nor
> `BudgetExceededException` exists as a class — the `checkBudget()` snippet below
> is the original design intent. Nothing in the backend accumulates token spend or
> pauses extraction. The YAML and Java below are recorded, not read.

```yaml
app.memory.cost:                     # NOT READ BY THE BACKEND
  monthly-budget-usd: 50.00
  alert-threshold-percent: 80       # Alert at 80% of budget
  pause-at-budget: true             # Pause extraction when budget exceeded
```

```java
// Cost tracker
private final AtomicReference<BigDecimal> monthlyCost = new AtomicReference<>(BigDecimal.ZERO);

private void checkBudget() {
    BigDecimal budget = new BigDecimal(costConfig.getMonthlyBudgetUsd());
    BigDecimal threshold = budget.multiply(new BigDecimal("0.8"));
    
    if (monthlyCost.get().compareTo(threshold) > 0) {
        log.warn("Monthly cost ${} approaching budget ${}", monthlyCost.get(), budget);
        if (costConfig.isPauseAtBudget() && monthlyCost.get().compareTo(budget) > 0) {
            log.error("Monthly budget exceeded, pausing extraction");
            throw new BudgetExceededException("Monthly cost budget exceeded");
        }
    }
}
```

### 23.6 Cost-Effectiveness Analysis

**Question: Is extraction worth the cost?**

**Extraction value**:
- ICL prompt includes structured preferences → better AI responses
- Personalization without re-reading all conversations
- One-time extraction cost, repeated use in every ICL prompt

**ROI per extraction call**:
- Cost: $0.0005 (GPT-4o-mini)
- ICL context: ~500 tokens of structured preferences
- Used in: Every subsequent conversation (10-100 calls/day)
- Value: 500 tokens × 10-100 conversations = 5000-50000 tokens of context value

**Conclusion**: Extraction is highly cost-effective. The initial cost is amortized over many subsequent uses.

**Refinement value**:
- Keeps memory quality high (removes duplicates, merges related observations)
- Reduces ICL prompt size (fewer redundant observations)
- Prevents memory pollution

**ROI per refinement call**:
- Cost: $0.005 (GPT-4o-mini)
- Value: Removes 1-2 low-quality observations
- Saves: ~100-200 tokens per future ICL prompt

**Conclusion**: Refinement has moderate cost-effectiveness. Deep refinement should be infrequent (weekly) to balance cost vs quality.

### 23.7 Cost Configuration

> **These keys are what the backend actually reads.** An earlier version of this
> section showed `app.memory.extraction.schedule` and a `cost-control` block.
> **Neither exists.** No code reads them, so setting them has no effect and
> produces no warning. The configuration that does exist is below.

**Extraction** — `backend/src/main/resources/application.yml`:

```yaml
app.memory.extraction:
  enabled: ${EXTRACTION_ENABLED:false}       # default false
  initial-run-max-candidates: ${EXTRACTION_MAX_CANDIDATES:100}
  max-observations-per-batch: ${EXTRACTION_BATCH_SIZE:20}
  max-batches-per-template: ${EXTRACTION_MAX_BATCHES:10}   # inert at these defaults
  templates:
    - name: "user_preference"                # the only one configured
```

> **Reading these defaults as if they described a first run is the single most
> expensive misconception in this section.** `initial-run-max-candidates` is applied
> on *every* invocation, and the default template list has one entry, not the five
> the §23.2 scenario assumes. §23.2b explains what the cap silently excludes.

**There is no extraction schedule, and extraction never runs on a timer.** It is
entirely event-driven, from exactly two reachable call sites:

| Trigger | Call site | Reached by |
|---------|-----------|-----------|
| Explicit request | `ExtractionController:172` → `runExtraction` | `POST /api/extraction/run` |
| Session `userId` change | `SessionController:327` → `reExtractForSession` | `PATCH /api/session/{id}/user` |

A third call site exists at `MemoryRefineService:251` (the last step of
`deepRefineProjectMemories`), but **that method has no callers anywhere in the
codebase** — only javadoc in `StructuredExtractionService` mentions it. Treat it
as unreachable, not as a background trigger.

**Refinement** — the real keys:

```yaml
app.memory:
  refine-enabled: ${MEMORY_REFINE_ENABLED:true}      # yml, default true
  refine-schedule-interval-ms: 300000                # @Scheduled, default 5 min
  refine:
    delete-threshold: ${MEMORY_REFINE_DELETE_THRESHOLD:0.3}
    cooldown-days: ${MEMORY_REFINE_COOLDOWN_DAYS:7}
    stale-days: ${MEMORY_REFINE_STALE_DAYS:30}
```

`scheduledRefineAll` fires on that fixed rate (a `fixedRateString`, not a cron
expression — there is no cron schedule anywhere in the backend) and calls
`quickRefine(project, 10)`. `quickRefine` has no other caller: an earlier
version of this section described it as running "every session end", which it
does not. Because it is a fixed rate rather than a calendar schedule, raising
the interval raises the gap between runs instead of moving a 3am run to a
different hour.
