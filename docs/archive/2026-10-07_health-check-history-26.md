1. **`QualityDistribution.Total()`** —— 假设「四桶之和未必等于总数」，**被推翻**。

2. **`FeedbackRequest`** —— 确有生产调用点（`client_methods.go:202`）。

   差点误判成「死 DTO」；实际接收者是 `*httpClient`。**又一次仪器错误在采信前拦下。**

**由此挖出 P2-93。** 后端 `MemoryController.java:253-254` 是决定性两行：
`if (request.comment() != null) { obs.setUserComment(...) }` ——
**缺失则保留，显式空串则覆盖**，所以清空评论的唯一表达就是发 `""`。

| SDK | 判空写法 | `""` 上 wire？ | 能否清空 |
|---|---|---|---|
| Go | `json:"comment,omitempty"`（`misc.go:26`） | ❌ | **否** |
| JS | `if (req.comment)`（`client.ts:355`） | ❌ | **否** |
| Python | `if comment:`（`client.py:615`） | ❌ | **否** |
| **Java** | `if (comment != null)`（`CortexMemClientImpl.java:252`） | ✅ | **是** |

**Java 是唯一正确的那个，且它的注释明确写出了这个区分** —— 说明该语义被设计过，只是另三家没跟上。

**活体实测（三段式）**：观测 `32ca7c75-…`，直查 `mem_observations.user_comment`。
置入 `restored` → Go/JS/Python 体（省略 comment）→ **仍是 `restored`，未清空**；
Java 体（`comment:""`）→ **已清空**。

**第一版把 C 段跑在了已被 B 段清空的状态上**，那样的 C **无法区分**「保留原值」与
「也清空了」，读数必然假阳。**重置评论后重跑**才得到上表 —— 这才是有效的负对照。

**不单方面修**：API 文档只写「Optional feedback comment」，**从未声称可清空**，
四家 README 也都没这么写 → 无失实陈述可照权威直接改；而修法会**改变现有调用方实际发出的报文**
（从未设过评论的用户会突然开始发 `""`），属对外契约变更。
**建议作者先裁定语义**：`comment: ""` 到底该不该表示「清空」？
若该，三家同步改；若不该，则应在 API 文档补一句「空评论不生效」，把隐性变显性。

**P2-94：module 路径多了一节，45 处。** 文档把
`github.com/…/go-sdk/cortex-mem-go` 写成 `…/go-sdk/cortex-mem-go/**cortex-mem-go**`。

`grep '^module .*cortex-mem-go/cortex-mem-go' --include=go.mod` **零命中**，

**受控实验（含负对照）**——两个临时探针模块，`replace` 指向同一真实目录：

| 探针 | import 路径 | `go build ./...` |
|---|---|---|
| **A（文档写法）** | `…/cortex-mem-go/cortex-mem-go` | **失败 EXIT=1**：`no required module provides package …/go-sdk/cortex-mem-go/dto` |
| **B（正确写法，负对照）** | `…/cortex-mem-go` | **成功 EXIT=0** |

A 能被 Go 接受**纯粹因为探针自己写了 `replace` 把它伪造成模块**；去掉 replace 就不存在。
而 A 的报错本身极有说服力：SDK **自己的内部 import 是单节的**，一旦外部按双节引入，
SDK 立刻解析不了自己的 `dto` 包。

### 本轮踩到的仪器错误（六处，全部在采信前拦下）

①`grep -c` 无匹配时打印 0 **且**退出码 1，与 `|| echo 0` 叠加会产出「0\n0」；
②探针命令把 `rm` 串在 `&&` 链首，`rm` 失败导致后续 `&&` 全部不执行，
heredoc 仍运行 → **在仓库根目录误建了 `main.go`**，已用可恢复删除清掉、工作区已复原；
③探针 `go.mod` 漏写 `require` 关键字，报 `unknown directive` —— 修正后才取到读数；
④**把被截断的显示当成了整行**：用 `grep … | cut -c1-120` 看第 312–316 轮的归档指针，
得出「以 `（第 326 轮；` 结尾、括号未闭合」的结论并准备「顺手修掉」——
读整行才发现实为 `（第 326 轮；第 312 轮）。`，**本来就好好的**。
脚本里为此留了一个**只校验、不改写**的断言，它匹配到 **0** 处待修，
这个 0 本身就是「那些指针从未坏过」的证据。**缺陷在读取手段，不在文件。**
⑤**自己的算术错**：312–316 是**五**轮，我一路写成「六条指针」，
连归档说明和脚本注释都写错了；断言打出 `checked: 5` 才暴露出来。
⑥**断言自身写错**：压缩校验里有一条「工作文件 ∪ 归档的轮次标题应等于原始轮次」，
但按设计契约，被迁的轮次标题**本来就既留在工作文件作锚点、又逐字进入归档块**，
各计两次是对的 —— 断言却按「不得重复」来判，于是误报 317–322 重复。
**是断言错了，数据没错**；改断言去表达真实契约，而不是去改数据迁就断言。
