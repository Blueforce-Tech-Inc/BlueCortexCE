# Backup / restore operational loop at 1M rows — 2026-11-05

Live, not a gate. `scripts/backup-restore-drill.sh` runs the whole operational
loop against a database with **1,000,198 observations and 1,000,198 vectors**:

1. `pg_dump -Fc -Z 6`
2. sha256 + `pg_restore --list` archive readability
3. restore into a throwaway database
4. row-count parity on six tables
5. replay a retrieval query on the copy and compare hit count + probe title
6. the nine-check integrity audit (`scripts/data-integrity-audit.py`)
7. drop and rebuild the HNSW index at `maintenance_work_mem = 4GB`, 2 workers
8. JSON report, then prune the dump (retention) and drop the copy

Raw report: `2026-11-05_ops-loop-1m.json`.

```
SOURCE_DB=cortexce_ops_1m REBUILD_HNSW=1 HNSW_WORK_MEM=4GB HNSW_WORKERS=2 \
INTEGRITY_AUDIT=1 REPORT_DIR=/tmp/drill-1m ZH_QUERY=capacity \
scripts/backup-restore-drill.sh
```

## What this run changed in the operational guidance

**Restore is index-build time.** `pg_restore` replays the `CREATE INDEX ...
USING hnsw` statement with whatever `maintenance_work_mem` the server has — on
this instance 64 MB. The build printed `hnsw graph no longer fits into
maintenance_work_mem after 898,013 tuples` and took ~40 of the 41 restore
minutes. The same build at 4 GB took **9.2 min**. Two ways to avoid paying it
twice:

- raise `maintenance_work_mem` **before** `pg_restore` (e.g. `8GB` at 1M rows),
  or
- dump **without** the vector index (drop it first, or use `--exclude-table`-level
  tooling) and rebuild once after restore with `REBUILD_HNSW=1`.

The drill keeps both paths measurable: stage 3 measures the restore as-is, stage
7 measures a tuned rebuild on the same copy.

**Disk budget ≈ 2.7× the source database.** Peak footprint was
source (19.6 GB) + play copy (15.2 GB) + dump (4.7 GB) = **39.5 GB** for an
18 GB live database. Provision at least `2 × pg_database_size + dump_size`
before running the loop on a production host.

**The source was ~4 GB larger than the copy.** 18 GB vs 14 GB after restore
means roughly 4 GB of heap bloat that `VACUUM (FULL)` or a tuned autovacuum
would reclaim; the copy was rebuilt compactly. Size the disk from the *copy*
number, not from the live one.

**Retention pruning ran.** With the defaults (`KEEP_DUMP` follows `KEEP=0`) the
verified dump is deleted at exit — the loop is an inspection, not an archive.
Set `KEEP_DUMP=1` to keep it as the backup and have dumps older than
`DUMP_KEEP_DAYS` (default 30) pruned. Verified on a 99-row rehearsal database
with `KEEP_DUMP=1 DUMP_KEEP_DAYS=1`: two 5-day-old
`cortexce_l2_flyway_rehearsal_*.dump` files were pruned and the fresh
382,243 B dump was kept (`kept dump ... (retention 1d)`). The same run also
proved that a probe that finds no rows fails the loop at stage 7 (exit 7)
instead of reporting a pass.

## Caveat

The container was shared with an unrelated `spring-ai-rag` benchmark during the
restore stage of this run (one foreign HNSW build on another database). Treat
the dump and restore timings as upper bounds; the HNSW stage (550.4 s) ran after
that load ended and is comparable to the quiet-host 801.6 s earlier the same
day.

## L2 gate

This loop is a live operator drill, not a unit test: it needs a database that is
already at the size being checked, so the gate stays on
`scripts/verify-local.sh`. The stage exit codes (2–11) and the JSON verdict are
the machine-readable contract; `docs/DEPLOYMENT.md` §8 documents them.
