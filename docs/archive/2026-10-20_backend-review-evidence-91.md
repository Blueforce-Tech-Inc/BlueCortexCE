### P2-174: Java SDK 的**重试范围**（README 明写「25 个方法里 10 个会重试」）**零测试钉住** —— 整个模块把 `retry.max-attempts` 设为 1，于是「会重试」与「不会重试」发出去的请求数**完全一样**

- **Scope**: → [scope-9][a6]
- **Problem**: Java SDK 的 README 用一整节写清重试范围：**25** 个 public 方法里 **10** 个会重试
  （5 个捕获/异步调用耗尽后吞错、3 个变更类方法上抛、2 个抽取读方法上抛），其余 **15** 个**从不重试**；
  而另三家 SDK 只重试 3 个捕获方法 —— 这是一条**跨家契约**，调用方要照搬配置、或为某个方法写
  「避免重试」补丁，就得先知道它。
  但这条契约**零测试钉住**，根因很具体：模块内**所有**既有测试都在 `setUp()` 里把
  `retry.max-attempts` 设成 **1**，于是「会重试」与「不会重试」两种实现发出去的请求数**完全一样（1）**。
  已有的 5 个吞错契约用例（`recordObservation` / `recordUserPrompt` / `recordSessionEnd` /
  `triggerRefinement` / `triggerExtraction`）断言的是 `requestCount == 1` —— 而这个断言对
  **一个完全不重试的方法同样成立**。
  ⇒ 把 `recordObservation` 改走别的重试路径、或给 `search` 加上重试，**全模块的用例仍然全绿**；
  README 写的那一节，没有任何东西守着。
- **实测（实现侧逐个核对）**: `CortexMemClientImpl` 里有三个重试辅助方法与**恰好 10** 个调用点 ——
  `executeWithRetrySilent` 5 个（`recordObservation` / `recordSessionEnd` / `recordUserPrompt` /
  `triggerRefinement` / `triggerExtraction`）、`executeWithRetry` 3 个（`submitFeedback` /
  `updateObservation` / `deleteObservation`）、`executeWithRetryReturn` 2 个（`getLatestExtraction` /
  `getExtractionHistory`）；全文只有这三个 `for (int attempt ...)` 循环 ⇒ **没有第二条重试路径**。
  另三家的重试调用点各只有 **3** 个：Go `doFireAndForget`（`client_methods.go:53/65/80`）、
  Python `_fire_and_forget`（`client.py:324/353/389`）、JS `doFireAndForget`（`client.ts:182/195/209`），
  都是 `RecordObservation` / `RecordSessionEnd` / `RecordUserPrompt` ⇒ 差集 = **7**。
- **修法（本轮已修，Java SDK 侧，只加测试，SDK 主源码零改动）**: 新增 `CortexMemClientRetryScopeTest`
  （**37** 个用例）：
  ① **25** 个方法逐个断言请求数 —— 10 个重试方法 == **3** 次、15 个不重试方法 == **1** 次
  （用 **503**；**500 刻意不重试**，故不能用 500 当探针）；
  ② 10 个重试方法逐个断言「耗尽后吞错 or 上抛」（静默 5 / 上抛 5）；
  ③ **覆盖性断言**：用反射读 `CortexMemClient` 的 public 方法，与表里的行**集合相等**
  ⇒ 新增 public 方法必须先决定重试行为，删掉一行也会红；
  ④ **阳性对照**：同一个调用分别以 1 次与 3 次尝试跑 ⇒ 断言「请求数 1 vs 3」确实可被区分
  （防「探针测不出差异」这种最贵的失败）。
  用 `MockWebServer` 数请求、反射读接口，**不连后端、可离线跑**。
- **变异测试（三次各恰好 1 红；另一次阴性对照 0 红）**:
  - 变异 A：`recordObservation` 的调用点由 `executeWithRetrySilent` 改为 `executeWithRetry`
    ⇒ **恰好 1** 红（吞错/上抛断言）；范围断言仍绿（它仍然重试 3 次）—— 归因正确；
  - 变异 B：`submitFeedback` 的调用点由 `executeWithRetry` 改为 `executeWithRetrySilent`
    ⇒ **恰好 1** 红；
  - 变异 C：`executeWithRetrySilent` 的循环上界由 `maxRetries` 改为 `1` ⇒ **11** 红，
    **全部**落在 5 个静默方法（5 个范围断言 + 5 个吞错断言）与阳性对照上，
    **15 个不重试方法一个没红**；
  - 阴性对照：只把操作名的日志字符串改掉（行为零变化）⇒ **0** 红（证明用例不是「见改就红」）。
  每次变异后 `CortexMemClientImpl.java` 按 sha256 `f97b37ee62c15d12…` **逐字节还原**，
  `git diff src/main/` 为空。
