TITLE CONTRACT
--------------
Format: `<verb> <object> <key identifier>`.
- Pick the NARROWEST past-tense verb that describes this turn. Do not default to Added, Changed
  or Fixed when a narrower verb applies:
  - Fixed: a defect already produced wrong or failing behaviour, in non-security code.
  - Added: a NEW FILE or new independent entity ONLY — a new class, test file, migration, endpoint,
    plugin or module. Never use Added for a fragment inserted into an existing file.
  - Extended: a block or entry inserted into an existing non-document file (new probe, new plugin
    block, new configuration key, new dependency line).
  - Updated: existing content in an existing non-document file was replaced or reworded.
  - Changed: an existing setting, value or document section was edited. Use Set when the change
    is a single numeric value.
  - Refactored: the structure changed and behaviour is identical (delegation, extraction, dispatch).
  - Hardened: ANY security-domain change — authorization, access narrowing, secret masking,
    input validation, XXE/CSRF/injection/traversal defences, encryption, CORS. Use Hardened even
    when the defect was already reported: the security domain decides the verb, and `<type>`
    carries whether it is a bugfix. Never lead a security change with Fixed, Added or Changed.
  - Removed: a capability, key, file, dependency or credential was deleted.
  - Enabled / Disabled: an existing feature or setting was switched on or off.
  - Converted: the artifact's form changed (single-stage to multi-stage build, format migration).
  - Recorded: an ADR or decision record was written.
  - Documented: a new or edited section in an existing document (README, runbook, API reference).
  - Migrated: schema, data or platform moved to a new version.
  The verb describes the semantic action, not the file edit. A new test file is `Added`, but a
  class, probe or config entry inserted into an existing file is `Extended`; a new section in an
  existing document is `Documented`. Never encode defect origin in the verb — `<type>` carries
  bugfix versus refactor or change. Never use Raised, Improved or any verb outside this list.
- The object is what changed, named the way the requester would say it: "pagination",
  "login log", "connection pool", "log level", "line endings", "authorization", "parameterized
  test", "CORS policy". Name the capability in plain words, not only the annotation or class that
  implements it.
- End the title with the file path or class identifier when the change lives in a config, doc,
  deploy file or a single class: `... in application.yml`, `... in docs/API.md`,
  `... in infra/main.tf`, `... in WebClientConfig`. If that would exceed 100 characters, shorten
  the object wording; never drop the path suffix or an identifier.
- Copy EVERY identifier that names the changed artifact verbatim: class, method, function,
  test name, file name or path, configuration key, endpoint, image tag. Never translate,
  abbreviate, re-case or paraphrase them, and never drop one to keep the title short:
  `PaymentService` stays `PaymentService`, `computeIfAbsent` stays `computeIfAbsent`,
  `maximum-pool-size` stays `maximum-pool-size`, `/api/health` stays `/api/health`.
- A replacement keeps BOTH names: the literal or key that was replaced and the file that now
  holds it (`ACME_API_KEY` in `application.yml`, not just `application.yml`). A changed script or

FACTS CONTRACT
--------------
- A fact must be verifiable from the observed tool input/output. Do not infer, speculate or add
  opinions ("should be faster", "likely fixes", "this is better").
- 1-5 facts, each one self-contained statement, no pronouns.
- Every fact must contain at least one exact identifier, path, number or status code copied from
  the tool input/output; a fact without an anchor is not verifiable and will be discarded.
- Each fact must name the changed identifier AND the concrete value, behaviour or comparison it
  now has: a value (`canary.weight = 10`), a count (`780MB -> 210MB`), an error, or a status code.
- Do not spend a fact on process noise. "was added to <path>", "the file was edited",
  "lint passes", "tests are green" are not facts about the change unless they name the exact
  file or command AND the observed value.
- bugfix facts describe the broken behaviour and the concrete change:
  good `PaymentService throws PaymentNotFoundException for a missing orderId`;
  bad `payment code is now better`.
- feature/test-add facts describe the new capability or test:
  good `DailyReportTest#reportUsesBusinessTimezone pins 2026-11-01T23:30Z and expects 2026-11-02`;
  bad `added some tests`.
- refactor facts describe structure, not behaviour:
  good `InvoiceService delegates tax, rendering and mail to three collaborators`;
  bad `refactored everything`.
- Good: `infra/canary.yaml sets canary.weight to 10 for a 10 percent rollout`
- Bad: `helm lint passes for the canary configuration` (process noise, no value)

CONCEPTS CONTRACT
-----------------
- Choose EXACTLY 2 concepts from the closed list below. Never output one, never output three
  or more, and never invent a category.
- Slot 1 (what happened):
  1. `problem-solution` when the trace fixes a concrete defect (crash, wrong result, security
     hole, race, leak) or adds a test that pins such a defect. A restriction, hardening, config
     edit or deployment change with no reported defect is NOT `problem-solution`.
  2. `why-it-exists` when the trace is a decision record, ADR or policy that explains rationale.
  3. `what-changed` for every other change (config, deploy, docs, refactor, routine test).
- Slot 2 (what a future reader should remember), in this order:
  1. `pattern` when the turn introduces a reusable building block, structure or test scaffold:
     atomic primitive, graph fetch, extracted collaborator/strategy, map-based dispatch,
     parameterized cases, contract test, documented procedure. Documentation-only turns are
     `pattern` because the document becomes the reusable procedure or contract.
  2. `trade-off` when the change accepts a stated cost: pool size, replica count, memory cap,
     timeout, traffic weight, build or coverage overhead, disabling a capability.
  3. `gotcha` when the trace states a durable trap or default a later caller must guard against:
     null contract, platform locale or charset default, time/expiry boundary, regex complexity,
     resource leak, redaction rule. Do NOT use `gotcha` merely because the defect involved an
     edge case when the fix itself is the only lasting knowledge.
  4. `how-it-works` only when the trace explains a mechanism and makes no change at all; never
     use it to describe a turn that edited something.
  5. `what-changed` when none of the above applies.
- Defaults that decide the ambiguous cases: configuration-only turns are `trade-off`; deployment
  and CI turns are `trade-off` for sizing, limits or weights and `pattern` for a reusable
  pipeline or script; documentation-only turns are `pattern`; an ADR is `trade-off`.
- Closed list: `how-it-works`, `why-it-exists`, `what-changed`, `problem-solution`, `gotcha`,
  `pattern`, `trade-off`.
